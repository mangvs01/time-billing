# Time Billing 9.2-rc48 — notes de version (préparée, NON déployée)

rc48 = rc47 (en production) + BILL-FC1 + BILL-FA1FT + mot de passe à 10 caractères minimum (BMDP1, demande du propriétaire du 20/11) + guide en bref (`docs/GUIDE-EN-BREF.md`) + préparation de la QR-facture, TOUJOURS ÉTEINTE (BILL-QR-PRET). Version annoncée : `9.2-rc48` (app/app.py, tests de version). État figé : commit `7cc5abb`.

## Ce qui change pour l'utilisateur (5 phrases)
1. Un avoir pour la totalité d'une ligne dont le montant finit sur un demi-centime (par exemple 1,5 × 0,15 = 0,225, facturé 0,23) est désormais accepté, alors qu'il était refusé à tort.
2. Il n'est plus possible de créer deux adresses de facturation du même client dont le nom ne diffère que par les majuscules (« EGG FR » et « egg fr ») : l'application le dit en français (« … deux noms d'adresse ne peuvent pas se distinguer seulement par les majuscules et les minuscules… Choisir un autre nom »). Une adresse qui a déjà un tel « jumeau » (créé avant rc48) reste modifiable (contact, texte) tant qu'on ne change pas son nom (BILL-RC48-FIX, constat A).
3. Quand la base elle-même refuse une opération (restauration d'une sauvegarde JSON, création d'une note de crédit), le message est en français, sans texte technique anglais (constat G).
4. Le mot de passe de l'application doit avoir au moins 10 caractères (au lieu de 12) (règle appliquée quand on choisit un nouveau mot de passe ; détails : `docs/MOT-DE-PASSE.md`).
5. Rien d'autre ne change à l'écran (la QR-facture est préparée mais éteinte : `QR_BILL_ENABLED` vide dans les compose, factures identiques ; allumage en 6 étapes dans `docs/QR-ALLUMAGE.md`, après accord) : les autres modifications sont des protections internes de la base (une ligne de facture ou d'avoir ne peut plus être déplacée ou réécrite pour contourner les règles), invisibles tant que l'application est utilisée normalement.

## Migration (automatique au démarrage, additive)
- Se fait par `app.init()` au démarrage, aucune commande à lancer, aucune table ni colonne ajoutée, aucune ligne modifiée.
- Ajoute 1 index (`idx_billing_addresses_label_nocase`) et 5 déclencheurs (`credit_line_upd_no_move_frozen`, `credit_line_upd_same_invoice`, `credit_line_upd_same_vat_mode`, `credit_line_upd_within_line`, `invoice_line_no_move_to_issued`) ; remplace `credit_lines_within_line` (même nom, nouvelle formule d'arrondi).
- Si la base contient déjà deux adresses d'un même client à la casse près, l'index n'est PAS créé (rien n'est supprimé ni renommé) : l'application démarre, une note `billing_address_label_index_skipped` est écrite une fois dans le journal d'audit, le contrôle de schéma la signale, et l'application refuse quand même les nouveaux doublons.
- Restauration d'une sauvegarde JSON : un fichier contenant de tels doublons est signalé comme bloquant à l'aperçu, avant tout changement.
- **À faire avant la mise en ligne** : passer `python3 -I outils/controle_copie_rc48.py COPIE.db` sur une COPIE de la base de production (lecture seule ; procédure complète et attendus : `docs/revues-rc48/VERIFS-COPIE-PROD.md`). Recommandé : renommer sous rc47 toute adresse « jumelle » signalée AVANT la mise en ligne. Sinon, avec un doublon à la casse près en production : l'application démarre, mais le contrôle de schéma passe au rouge (`30-rehearse.sh` NO-GO, `50-verify.sh` échec, `verifier-sauvegarde.sh` « non exploitable ») et la restauration JSON de cette base est refusée tant que le doublon existe (message : renommer l'une des deux adresses dans l'écran Adresses puis refaire la sauvegarde).
- **Contrôle de schéma renforcé** (`app/schema_checks.py`, constat F) : il vérifie maintenant, en plus de l'index d'adresse, la présence ET le texte des 5 nouveaux déclencheurs et de la nouvelle formule d'arrondi du plafond d'avoir (`credit_lines_within_line`). Un retour arrière partiel, ou un déclencheur resté à l'ancienne formule, est signalé par `50-verify.sh` / `verifier-sauvegarde.sh`.

## Retour arrière rc48 → rc47 (testé contre le vrai code rc47, `outils/repeter_migration_rc48.py` sections 4, 5, 7, 8)
**Recommandé : l'outil `outils/retour_rc47.py`**, application arrêtée, sauvegarde de la base faite avant.
- `python3 -I outils/retour_rc47.py base FICHIER.db` : simulation (ne modifie rien) ; avec `--oui` : copie de sécurité vérifiée (`FICHIER.db.avant-retour-rc47-<horodatage>`), retrait des 6 objets de rc48 (1 index + 5 déclencheurs), plafond d'avoir remis à celui de rc47, schéma vérifié (texte SQL identique à une base rc47 neuve), une ligne `rollback_rc47_schema` au journal d'audit. Aucune ligne métier n'est touchée (empreinte identique, vérifiée). Puis démarrer rc47. Un nouveau passage de rc48 refait la migration tout seul. Ne jamais lancer rc48 sans avoir remis son code : rc48 recrée ces objets à chaque démarrage.
- **Pourquoi plutôt que « ne rien défaire »** (constat D, reproduit) : rc47 ne connaît pas l'index d'unicité des adresses. Si la liste commune contient « egg fr » et le client d'origine « EGG FR », rc47 REFUSE DE DÉMARRER sur une base rc48 laissée telle quelle (`UNIQUE constraint failed: billing_addresses…`). Après l'outil, rc47 démarre. Sans cette configuration d'adresses, laisser la base rc48 telle quelle fonctionne aussi (rc47 démarre, ne modifie aucune donnée, les protections de rc48 restent actives) mais l'outil reste la voie sûre, car elle ne dépend pas des données.
- **Restaurer une sauvegarde JSON faite sous rc48 pendant que rc47 tourne** (constat C, reproduit) : rc47 reconstruit la base avec SON ancien plafond d'avoir et REFUSE le fichier s'il contient un avoir total sur une ligne à demi-centime (message en français, base inchangée). Marche à suivre exacte, au choix : (a) restaurer le **fichier SQLite** de la sauvegarde (aucun contrôle de ce type) ; (b) `python3 -I outils/retour_rc47.py json SAUVEGARDE.json SORTIE.db` : produit, avec le code rc48, un fichier SQLite au schéma rc47 contenant exactement les données du JSON (contrôles d'intégrité de la restauration compris ; vérifié : rc47 démarre dessus et ne recrée rien), à installer comme base application arrêtée. L'outil refuse d'écraser un fichier existant.
- **Garde-fous de l'outil (BILL-RC48-FIX2, constat N-1 de la 2e revue)** : l'outil n'agit QUE sur les chemins donnés en argument, jamais sur la base « par défaut » (`DB_PATH`). Le mode `base` n'importe pas l'application du tout. Tout chemin sous `/opt/time-billing-v9` (liens symboliques résolus) ou égal à `DB_PATH` est REFUSÉ (code 1, rien fait) sauf option explicite `--confirmer-chemin-production` : à n'utiliser que pour le retour `base` de la procédure, application arrêtée, sauvegarde faite. Tests : `CD_return_tool` (base visée par `DB_PATH` octet pour octet identique après `json`, y compris avec un fichier refusé ; refus des chemins de production ; `base` n'importe pas `app.app`).
